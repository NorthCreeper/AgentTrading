## 3. 行情数据核对与保护

当前会话历史中读取 119,003 个行情帧、238,006 份单侧订单簿快照：11,361 份源年龄超过 3 秒；12,660 次相邻同 token 源时间重复；发现 2 次源时间倒退，没有发现同源时间但档位内容改变。

这些是已记录快照的计数，不是市场停更时长百分比。早期源异常可能根本没有形成行情帧，因此不能只靠该分母衡量所有丢失时间。

额外进行了约 55 秒的只读 REST/WebSocket 同步取样：90 份 REST 快照均未超过 3 秒，最大源年龄 1,480 毫秒；WebSocket 有订单簿、价位变化、成交和价格步长事件。说明取样期间两条渠道在更新，**不能据此解释此前全部陈旧快照，也不能证明安静盘口上的源时间等同于“最后变化时间”。**

原 `receivedAt` 是两侧轮询都完成的时间，不是每侧实际接收时刻。P0 增加 `transportReceivedAt`，兼容保留原字段和原交易有效期计算。本次前瞻数据里，二者差值中位数 1 毫秒、最大 5,009 毫秒，后续研究不能将原字段直接视为单侧网络到达时间。

新保护上线后实际拦截了一次源时间倒退 35 毫秒的快照。它被写入拒绝诊断，没有送入新的动量帧。未修改 3 秒盘口有效期，也没有把陈旧行情改成新时间。

## 4. 低频原因：先区分观察次数与交易机会

历史快照中，当前会话有 42,918 次方向候选通过策略检查，其中 36,381 次位于已记录持仓区间，约 **84.77%**。这是按历史开平仓区间回看得到的归因，不包含所有在途订单状态，也不代表错过了 36,381 笔独立交易。

P0 上线后的新记录进一步拆出了同时存在的阻断条件。前瞻窗口为 **08:45:57–18:58:02 HKT**，含 123 个有行情帧的轮次；总表另包含 2 个仅有相关成交/结算事件的轮次。

| 逐级观察统计 | 次数 |
|---|---:|
| 独立记录的行情帧 | 36,392 |
| 当前数据条件可用 | 29,934 |
| 连续窗口可用 | 25,807 |
| 存在窗口内动量信号 | 17,022 |
| 同方向信号及成本/深度全部通过 | 14,372 |
| 上述条件与账户条件同时通过 | 63 |
| 实际买单提交 | 63 |
| 有实际买入成交 | 63，全部完成该次买入预算 |

前五级是行情观察次数，最后两级是执行事件，不能将“63/36,392”解释为订单成交率。所有帧的独立诊断资格与主策略选择结果均一致，没有发现不一致。

在 14,372 次已通过信号与成本检查的观察中：

- 12,182 次存在已持有仓位；其中 8,238 次具体处于盘口到期后等待核验/释放。
- 6,071 次已经使用过该轮开仓机会。
- 两类阻断可以同时成立，不能相加作为互斥占比，也不能据此直接决定放开单仓位或单轮次数。

结论：**当前少下单的重要原因是仓位和已使用机会，而不只是信号门槛。** 优先比较不同持有/退出方式的单位账户时间收益，比盲目降低入场条件更有依据。

## 5. “持有很久”主要包含了什么

历史当前会话的 191 笔完成交易，开仓至该轮结束前的可交易持有时长中位数为 **143.638 秒**。其中 82 笔结算交易，到期后的仓位占用中位数为 **728.726 秒（12.15 分钟）**，90 分位为 857.107 秒。标签核验通过后至本地模拟入账的中位数仅 **0.017 秒**。

因此，不能把账面记录中的十几分钟都解释为策略主动长期持有；主要等待发生在核验通过之前。

新前瞻窗口内共有 1,436 次完成的结算检查，其中 **790 次 Gamma 已标记 resolved，但 CLOB 仍未关闭**。可检查队列长度中位数 2、最大 3。检查次数不是等待时长比例，但明确证明部分等待来自两接口状态不一致，不能全部归咎本地队列堆积。

一个完整案例：轮次 `btc-updown-5m-1789864500` 于 08:40 到期；08:46 起的多次检查中 Gamma 已结算而 CLOB 未关闭，直到约 08:52:26 两边通过核验才将剩余 1.25 份按官方结果记入模拟账户。之后自动策略自然完成下一笔开仓，没有人为清仓或制造结果。

后续应检验：现有双接口终态条件与真正可验证、可兑付时点的关系；核验轮询可减少多少额外延迟；单仓位下这种等待具体损失多少后续机会。不能仅为了降低等待，就依据一个接口的显示状态提前模拟支付。
