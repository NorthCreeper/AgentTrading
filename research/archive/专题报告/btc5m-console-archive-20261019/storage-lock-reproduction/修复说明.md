# 档案读取与状态原子保存争用

正式故障发生在 `state.json` 原子替换时，错误为 EPERM。旧档案读取器在刷新目录时，以异步方式打开该文件读取会话编号；同一 Node 进程的保存函数在替换失败后同步等待最多 310ms。若读取句柄尚未关闭，同步等待会阻止异步关闭继续推进。

本目录的 `reproduce.mjs` 仅在系统临时目录内建立带有虚构数值的文件，并使用原有原子保存模块。异步读取句柄仍打开时，保存六次重试后 EPERM，旧文件及失败候选均保留；等待异步句柄关闭后，同样保存成功。结果记录在 `reproduction-result.json`。这证明了与线上源路径一致的可触发机制；并未识别或排除其他进程造成的文件占用。

最小修复删除档案读取器对状态文件的异步访问。服务端直接提供控制器内存中的当前会话编号；每次访问即时判断，不受目录缓存影响。提供者缺失、异常、无效或返回 Promise 时，拒绝运行目录内的 JSONL 读取。活跃会话的主日志与各分日志均拒绝；原有状态、私密文件、链接及清单边界拒绝规则保留。路径检查过程中会话发生变化，也会在打开前后重新拒绝。

生产代码仅修改 `dashboard/research-archive.mjs` 与 `dashboard/server.mjs`；金融控制器与 `dashboard/atomic-json.mjs` 保持原字节。新的源登记使用独立 `ray-audit-storage-fix/registration.json`，原有登记不覆盖。

针对性测试 21 项全部通过，包括新增的四项：即时会话切换及无效提供者拒绝、档案查询与原子保存并发且零异步账本读取、路径检查期间变为活跃会话的拒绝，以及服务端从内存提供当前身份。此前测试清理等待问题发生在新建的临时 HTTP 服务中，已补齐响应消费和连接关闭；未控制正式服务或账户。
